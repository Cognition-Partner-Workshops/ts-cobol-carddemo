In short

Once a month the mainframe job INTCALC charges interest on card accounts. This plan replaces that one job with a Java 21 / Spring Batch job on PostgreSQL 15 and leaves everything around it where it is. Other mainframe jobs and the online screens keep using the same files, so the new job gets a fresh copy of four files before each run and hands back two results: the new interest transactions and the updated account balances. The new job first has to produce exactly what the old one produces, known oddities included, on 7 recorded cases and then on real cycles run side by side, before it takes over.

Every item on this page is PROPOSED and names the role that has to confirm it. Open business questions are not settled here: they stay in the decision register and are built as the mainframe behaves today.

Job, transaction and restart boundaries
  • Job: one job, interestCalcJob, replaces INTCALC.STEP15; steps load, calculate, export. Every launch is a new run (INT-H02 as coded: no guard against a second run).
  • Transaction: the load commits one table at a time; the calculation commits whole accounts - an account's interest transactions and its balance update together, never split; the export moves finished files into place.
  • Restart: load and export are repeated; the calculation continues after the last committed account and ends with the same rows as an uninterrupted run (REL-11). The mainframe job has no restart.
  • Last account: gets its transactions but, as coded, no balance update (INT-Q04).
Rules of coexistence with the jobs that stay
  • The mainframe files stay the system of record (REL-02); the replica tables are replaced before every run.
  • The run happens between CLOSEFIL and OPENFIL, so the online programs that rewrite ACCTDATA are shut out as today.
  • Between unload and write-back no mainframe job may write ACCTDATA; the write-back replaces a record only if it still equals the unloaded image. The order against POSTTRAN is not in the scheduler exports (INT-H06).
  • Only the records of updated accounts are written back (REL-03); TCATBALF, DISCGRP and CARDXREF never are.
  • The exported transactions are cataloged as SYSTRAN(+1), so COMBTRAN reads them as today (REL-09).
